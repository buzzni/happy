# Happy 대화 프로세스 최적화

2026-11-22 · Saycode의 Claude·Codex 대화 시작 개선

## 적용 범위

Windows와 Mac 데스크탑의 로컬 실행기와 등록된 Linux 작업 머신에서 Claude·Codex 새 대화의 Happy 모듈을 재사용한다. 개인 사용과 조직 로그인 모두 적용된다. 작업 실행기 하나가 시작 시 설치본 모듈을 메모리에 보관하고 여러 대화에 공급한다. 각 대화는 보내기를 누른 시점에 기존 계정 선택, 작업 폴더 확인, 권한 설정, 공급자 실행 절차를 거친다.

Mac과 Windows의 로컬 실행기는 앱과 함께 시작한다. 등록된 Linux 작업 머신은 해당 머신에서 데몬을 띄울 때 준비한다. 원격 대화에는 작업 실행기가 돌아가는 머신의 OS가 적용된다. 터미널에서 직접 시작하거나 명시적으로 tmux 프로필을 사용하면 기존 CLI 경로로 실행한다.

두 모드의 속도 실측에서는 Claude와 Codex 프로세스를 전송 뒤에 시작했다. 공급자별 사전 실행과 여러 대화의 공급자 프로세스 공유는 이 결과를 기준으로 별도 평가한다.

## 실행 흐름과 장애 진단

1. `bundle-resident-session.mjs`는 Windows용 ESM 모듈을 `dist/win32-resident`에 묶는다. 샌드박스 런타임의 JavaScript와 Lodash도 포함해 보안 PC에서 반복되던 파일 조회를 줄인다. Windows에서는 샌드박스 런타임의 기존 플랫폼 판정이 적용된다.
2. 동기 ESM 로더 훅을 지원하는 Node 데몬이 설치본 모듈을 한 번 읽는다. Windows는 전용 번들을 읽고, Mac과 Linux는 설치본 `dist`의 최상위 ESM 파일을 원래 URL에서 제공한다. Mac과 Linux의 샌드박스와 네이티브 의존성은 기존 파일 경로를 사용한다.
3. 모듈은 루프백 주소에서 해당 자식 실행기에만 공급한다. 데몬이 직접 띄우는 자식과 Windows 네이티브 도우미가 시작하는 자식은 자기 프로세스에서 코드를 평가하고 공급자를 시작한다. 모듈 준비는 대화나 모델 호출을 만들지 않으며 작업 폴더·계정·메시지를 읽지 않는다.
4. 준비가 끝나지 않았거나 연결이 닫히면 설치본에서 기존 CLI 경로로 실행한다. Node 로더가 지원되지 않는 환경도 기존 경로를 사용한다. 검수용 데몬 시작에 `HAPPY_DISABLE_RESIDENT_MODULES=1`을 적용해 같은 빌드의 디스크 경로를 비교할 수 있다.
5. 데몬 종료·교체 시 모듈 호스트를 닫는다. 외부 도구나 다른 세션에는 모듈 호스트의 인증 환경값을 상속하지 않는다.

## 관측한 지연과 실측

Claude 시작 과정에서 로컬 Lodash 파일 읽기가 640회 관측됐다. 상주 번들에 이 의존성을 포함하자 모델 호출 없이 실행 코드를 불러오는 시간이 2.541~2.683초에서 0.657초로 줄었다. Happy 직접 검수에서 Codex GPT-6.1 Terra Low의 첫 답변은 같은 실행 경로에서 18.776초에서 15.865초로 줄었다. 준비된 Claude를 인수한 Happy 직접 검수는 8.232초였으며 아래 앱의 일반 공급자 시작과 조건이 다르다.

| Windows Saycode 개발 검수 환경 | Claude Opus 5.5 High | Codex GPT-6.1 Terra Low |
| --- | ---: | ---: |
| 개인 사용의 일반 새 채팅 | 14.151초 | 7.870초 |
| 조직 로그인과 등록 작업 PC의 프로젝트 새 대화 | 9.276초 | 10.134초 |

표는 2026-11-22 개발 검수에서 보내기 클릭부터 첫 답변 텍스트의 화면 프레임까지 공급자별 한 회차를 잰 결과다. 각 모드의 두 대화에서 같은 Happy 데몬의 상주 모듈을 확인했다. 앞선 조직 프로젝트의 Claude 32.883초는 이전 Happy의 기록이다. 공급자 실행 파일과 실행 조건 전체를 고정한 개선 폭은 산출하지 않았다. 최종 PR 브랜치의 값을 다시 잴 때는 위 기록을 참고값으로 사용한다.

같은 PC의 VS Code에서 Claude는 새 패널 두 개에 각각 실행기를 준비했고, Codex 확장은 전날부터 살아 있던 같은 app-server를 새 패널에서도 유지했다. 서로 다른 모델·도구 조합의 첫 답변 시간은 직접 비교하지 않는다.

## 검수 재현 절차

1. Happy·Desktop 커밋과 빌드 버전, Node·공급자 실행 파일 버전, 계정 유형, 모드, 폴더, 모델·추론 강도를 남긴다. 설치된 업무용 앱과 별도인 검수 프로필을 사용한다.
2. Happy에서 각 모델에 가상 산수 질문을 보내 정상 답변을 확인한다. `daemon-session-startup.log`의 `[timing] resident Happy modules ready`와 대화 PID를 대조한다. 상주 경로의 효과를 분리할 때는 같은 검수 데몬에서 상주 옵션만 바꾼다.
3. Happy 검증 후 동일 후보를 연결한 검수 앱을 연다. 개인 사용의 일반 새 채팅과 조직의 등록 작업 PC 프로젝트에서 같은 모델·추론 강도로 보낸다. 보내기 버튼 클릭과 가상 질문의 첫 실제 답변이 표시된 프레임을 재고 첫 로딩 표시는 별도로 기록한다.
4. 답변, 대화 PID와 데몬을 대조한다. 회차를 마친 뒤 데몬의 세션 목록과 PID를 확인한다. 여러 회차를 번갈아 재고 중앙값과 범위를 함께 남기면 초기화 개선과 모델 응답 변동을 구분할 수 있다.
5. 네이티브 종료 도우미가 있는 Windows 시험판에서 정상 앱 종료를 확인한다. 일반 개인 개발 빌드는 대화가 종료된 뒤에도 `Standalone drain unsupported or invalid capability`를 표시했다. 세션 종료 확인 기능이 없는 검수 빌드였고, 실행 중인 대화가 0개인 것을 확인한 뒤 해당 검수 데몬에 정상 종료를 요청했다.

가상 질문, 시각, PID만 기록한다. 로그인 파일, 제어 인증값, 설정의 비밀, 실제 대화 내용은 검수 기록에 복사하지 않는다.

## Mac·Linux 릴리스 후 실기 검수

### Mac 데스크탑

1. 이번 Happy 릴리스가 포함된 Saycode 버전을 설치하고 앱을 완전히 종료했다가 다시 연다. 앱 버전과 릴리스에 포함된 Happy 버전을 기록한다.
2. 개인 사용에서는 내 PC에 연결한다. 조직 사용에서는 등록된 작업 PC 목록에서 지금 검수하는 Mac을 선택한다. 사용할 수 있는 모드마다 Claude와 Codex를 골라 각각 새 대화를 시작한다.
3. 두 공급자의 첫 답변·후속 답변과 작업 표시 종료를 아래 공통 기준으로 확인한다. 모듈 기록은 앱이 선택한 Happy 홈의 `logs/daemon-session-startup.log`에서 확인한다. 기본 설치의 개인 사용 홈은 `~/.happy_local`이고, 조직 사용은 해당 작업 PC의 등록 프로필이 쓰는 홈을 확인한다.

### 등록된 Linux 작업 머신

1. 데몬이 사용하는 사용자와 Node 환경에서 Happy를 발행된 버전으로 업데이트한다. npm 전역 설치를 사용 중이면 `npm install -g '@buzzni/happy-cli@<릴리스 버전>' --prefer-online`에서 버전을 실제 발행값으로 바꿔 실행한다. `happy --version`과 `node -p "typeof require('node:module').registerHooks"`로 설치 버전과 로더 지원 여부를 확인한다. 로더 확인은 `function`이 기대값이다.
2. 기존 운영 방식으로 데몬을 다시 기동한다. 서비스로 관리 중이면 같은 서비스를 사용한다. 데몬과 같은 Happy 홈에서 `happy daemon status`를 확인하고, `daemon.state.json`의 `startedWithCliVersion`이 업데이트한 버전과 같은지 확인한다. 버전과 PID만 기록한다.
3. Saycode에서 등록된 Linux 머신을 선택하고 검수 프로젝트에서 Claude와 Codex 새 대화를 각각 시작한다. 일반 대화 시작 경로를 사용한다. 기본 Happy 홈의 로그는 `~/.happy/logs/daemon-session-startup.log`에 있고, 데몬에 `HAPPY_HOME_DIR`을 지정한 경우에는 그 홈의 로그를 사용한다.

### 공통 판정 기준

- Claude와 Codex 새 대화에 각각 `2+3의 답을 숫자만 적어줘`를 보내 `5`가 표시되는지 확인한다. 같은 대화에서 `방금 답에 1을 더한 값도 숫자만 적어줘`를 보내 `6`을 확인한다. 응답이 끝나면 작업 표시가 해제되어야 한다.
- 전송 시각으로 각 시작 기록을 찾아 `[timing] resident Happy modules ready`와 대화 PID를 확인한다. 연속한 새 대화는 각각 다른 대화 PID를 쓰면서 동일한 Happy 데몬에서 시작해야 한다. Happy 홈의 `daemon.state.json`에 있는 데몬 PID를 검수 전후로 비교한다. 앱이나 데몬이 막 켜진 직후에는 준비가 아직 끝나지 않아 기존 경로로 시작할 수 있다. 데몬을 켜 둔 상태에서 새 대화를 한 번 더 보내 확인한다.
- 첫 답변 속도는 보내기 클릭부터 첫 답변 텍스트가 보일 때까지 잰다. OS, 앱·Happy 버전, 계정 모드, 공급자·모델, 각 회차의 시간, 모듈 준비 로그 유무를 남긴다. 같은 조건의 반복 회차에서 기능 통과 여부와 첫 답변 시간을 각각 기록한다.

## PR과 배포 검증

Windows Node 22.23.1에서 Happy CLI 타입 검사·패키지 빌드, 상주 모듈 재사용·접근 제어·종료 후 폴백을 검증한다. 패키지에 실행기와 번들이 포함되는지, 상주·기존 경로의 버전 출력과 Claude·Codex 명령 진입이 정상인지 확인한다. 로더 훅 호환성이나 설치본 상대 경로가 바뀌거나 직렬화한 스냅샷이 32 MiB 한도에 가까워지면 이 경계를 다시 검토한다.

Happy CLI PR의 Windows·macOS·Linux 러너에서 모듈 재사용, 기존 경로의 호환성, 각 OS의 샌드박스 검사를 확인한다. Windows·Mac 검수 앱과 등록 Linux 머신에서 일반 대화를 시작해 최종 후보의 첫 답변·정상 종료를 별도로 측정한다. 릴리스 승인 뒤 [Happy CLI 릴리스 절차](happy-cli-release.md)로 발행하고 Desktop 런타임 핀을 갱신한다. Desktop 코드 PR은 머지 전에 해당 저장소의 macOS CI를 통과시킨다.
