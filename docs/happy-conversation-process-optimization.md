# Happy 대화 프로세스 최적화

2026-11-22 · Windows 보안 PC, Mac, Linux 작업 머신의 Saycode 대화 시작 개선

## 적용 범위

개인 사용과 조직 로그인 후 등록 작업 PC에서 Claude·Codex 새 대화의 반복 파일 조회를 줄인다. 앱과 함께 시작한 Happy 데몬 하나가 설치본 모듈을 메모리에 보관하고 여러 대화에 공급한다. 각 대화는 보내기를 누른 시점에 기존 계정 선택, 작업 폴더 확인, 권한 설정, 공급자 실행 절차를 거친다.

모듈 사전 로딩은 Windows·Mac·Linux 작업 실행기에서 활성화한다. Linux 작업 머신은 머신에 설치한 Happy 데몬이 같은 번들을 공급한다. 원격 대화에는 앱을 연 컴퓨터의 OS와 관계없이 작업 실행기가 돌아가는 머신의 OS가 적용된다.

Mac·Linux에서 설치본 `dist` 최상위 모듈만 같은 방식으로 공급한 첫 후보는 오히려 느렸다. 2026-11-22 Apple Silicon Mac과 Linux arm64 VM에서 `--version` 시작 시간(25회 번갈아 잰 중앙값)이 각각 715ms→839ms, 766ms→819ms였다. 이 경로는 `node_modules`를 포함한 모듈 약 2,180개를 불러오는데, 로더 `load` 훅이 모든 모듈에 걸리는 비용이 `dist` 18개를 메모리에서 읽어 아끼는 시간보다 크다. Lodash 640개는 모두 샌드박스 런타임이 불러온다. 그래서 Mac은 Windows와 같은 번들을 쓴다: `--version`이 678ms→427ms, 같은 Mac 작업 실행기에서 Codex 새 대화의 대화 프로세스 모듈 로딩이 약 1.0초→0.46초, 시작 요청부터 첫 답까지 6.55초→5.42초였다(같은 빌드에서 상주만 바꿔 각 3회 중앙값). Claude·Codex 대화 직전까지는 약 0.27초 줄었다. Mac 샌드박스는 Seatbelt 프로필을 생성하므로 번들로 묶어도 패키지 기준 파일을 찾지 않는다. 묶은 샌드박스 런타임에서도 허용 폴더 쓰기만 되고 바깥 쓰기와 네트워크가 막히는 것을 확인했다. Linux는 샌드박스 런타임이 자기 모듈 위치 옆에서 seccomp 필터(`vendor/seccomp/<arch>`)를 찾고, 못 찾으면 경고만 남기고 unix 소켓 제한 없이 실행한다. 그래서 `bundle-resident-session.mjs`가 필터와 `apply-seccomp`를 `dist/vendor/seccomp`에 복사한다. Linux arm64 컨테이너(Node 22.23.5, bubblewrap)에서 같은 설정으로 묶은 런타임을 `dist/`에 두면 필터를 찾아 unix 소켓 생성이 `Operation not permitted`로 막혔고, 필터가 없는 위치에서는 막히지 않았다. 쓰기·네트워크 제한은 두 경우 모두 유지됐다. 같은 컨테이너의 `--version` 시작은 752ms→503ms였다(25회 중앙값).

두 모드의 속도 실측에서는 Claude와 Codex 프로세스를 전송 뒤에 시작했다. 공급자별 사전 실행과 여러 대화의 공급자 프로세스 공유는 이 결과를 기준으로 별도 평가한다.

## 실행 흐름과 장애 진단

1. `bundle-resident-session.mjs`는 Windows·Mac·Linux용 ESM 모듈을 `dist/win32-resident`에 묶는다. 샌드박스 런타임의 JavaScript와 Lodash도 포함해 반복되던 파일 조회를 줄인다. Windows에서는 샌드박스 런타임의 기존 플랫폼 판정이 적용되고, Mac은 생성한 Seatbelt 프로필을, Linux는 `dist/vendor/seccomp`에 복사한 seccomp 필터를 쓴다.
2. 동기 ESM 로더 훅을 지원하는 Windows·Mac·Linux 데몬이 설치본 번들을 한 번 읽는다. 메모리에서 공급 가능한 경우 루프백 주소에 제한하고, 인증값은 해당 자식 실행기에 전달한다. 상주 모듈 준비는 모델을 호출하거나 서버 대화를 만들지 않는다.
3. 전송 시 등록 PC 자식과 Windows 네이티브 도우미가 시작하는 개인 사용 자식 모두 기존 경계를 통과한다. 자식은 자기 프로세스에서 상주 코드를 평가하고 기존 방식으로 공급자를 시작한다. 작업 폴더·계정·메시지는 모듈 호스트가 다루지 않는다.
4. 준비가 끝나지 않았거나 연결이 닫히면 설치본에서 기존 CLI 경로로 실행한다. Node 로더가 지원되지 않는 환경도 기존 경로를 사용한다. 검수용 데몬 시작에 `HAPPY_DISABLE_RESIDENT_MODULES=1`을 적용해 같은 빌드의 디스크 경로를 비교할 수 있다.
5. 데몬 종료·교체 시 모듈 호스트를 닫는다. 외부 도구나 다른 세션에는 모듈 호스트의 인증 환경값을 상속하지 않는다.

## 관측한 지연과 실측

Claude 시작 과정에서 로컬 Lodash 파일 읽기가 640회 관측됐다. 상주 번들에 이 의존성을 포함하자 모델 호출 없이 실행 코드를 불러오는 시간이 2.541~2.683초에서 0.657초로 줄었다. Happy 직접 검수에서 Codex GPT-6.1 Terra Low의 첫 답변은 같은 실행 경로에서 18.776초에서 15.865초로 줄었다. 준비된 Claude를 인수한 Happy 직접 검수는 8.232초였으며 아래 앱의 일반 공급자 시작과 조건이 다르다.

| Windows Saycode 개발 검수 환경 | Claude Opus 5.5 High | Codex GPT-6.1 Terra Low |
| --- | ---: | ---: |
| 개인 사용의 일반 새 채팅 | 14.151초 | 7.870초 |
| 조직 로그인과 등록 작업 PC의 프로젝트 새 대화 | 9.276초 | 10.134초 |

표는 2026-11-22 개발 검수에서 보내기 클릭부터 첫 답변 텍스트의 화면 프레임까지 공급자별 한 회차를 잰 결과다. 각 모드의 두 대화에서 같은 Happy 데몬의 상주 모듈을 확인했다. 앞선 조직 프로젝트의 Claude 32.883초는 이전 Happy의 기록이다. 공급자 실행 파일과 실행 조건 전체를 고정한 개선 폭은 산출하지 않았다. 최종 PR 브랜치의 값을 다시 잴 때는 위 기록을 참고값으로 사용한다.

같은 PC의 VS Code에서 Claude는 새 패널 두 개에 각각 실행기를 준비했고, Codex 확장은 전날부터 살아 있던 같은 app-server를 새 패널에서도 유지했다. 서로 다른 모델·도구 조합의 첫 답변 시간은 직접 비교하지 않는다.

## 검수 재현 절차

1. Happy·Desktop 커밋과 빌드 버전, Node·공급자 실행 파일 버전, 계정 유형, 모드, 폴더, 모델·추론 강도를 남긴다. 설치된 업무용 앱과 별도인 검수 프로필을 사용한다.
2. Happy에서 각 모델에 가상 산수 질문을 보내 정상 답변을 확인한다. `daemon-session-startup.log`의 `[timing] resident Happy modules ready`와 대화 PID를 대조한다. 상주 경로의 효과를 분리할 때는 같은 검수 데몬에서 상주 옵션만 바꾼다.
3. Happy 검증 후 동일 후보를 연결한 검수 앱을 연다. 개인 사용의 일반 새 채팅과 조직의 등록 작업 PC 프로젝트에서 같은 모델·추론 강도로 보낸다. 보내기 버튼 클릭과 가상 질문의 첫 실제 답변이 표시된 프레임을 재고 첫 로딩 표시는 별도로 기록한다.
4. 답변, 대화 PID와 데몬을 대조한다. 회차를 마친 뒤 데몬의 세션 목록과 PID를 확인한다. 여러 회차를 번갈아 재고 중앙값과 범위를 함께 남기면 초기화 개선과 모델 응답 변동을 구분할 수 있다.
5. 네이티브 종료 도우미가 있는 Windows 시험판에서 정상 앱 종료를 확인한다. 일반 개인 개발 빌드는 대화가 종료된 뒤에도 `Standalone drain unsupported or invalid capability`를 표시했다. 세션 종료 확인 기능이 없는 검수 빌드였고, 실행 중인 대화가 0개인 것을 확인한 뒤 해당 검수 데몬에 정상 종료를 요청했다.

가상 질문, 시각, PID만 기록한다. 로그인 파일, 제어 인증값, 설정의 비밀, 실제 대화 내용은 검수 기록에 복사하지 않는다.

## PR과 배포 검증

Windows Node 22.23.1에서 최신 main을 바탕으로 만든 후보의 Happy CLI 타입 검사와 패키지 빌드가 통과했다. 상주 모듈 재사용·접근 제어·종료 후 폴백과 기존 Windows 실행 경로를 다루는 테스트 100개도 통과했다. 패키지에 실행기와 번들이 들어가고, 상주·기존 경로의 버전 출력과 Claude·Codex 명령 진입을 확인했다. Windows 시험판에서 최신 후보의 두 사용 모드와 정상 종료를 재검증한다. 로더 훅 호환성이나 설치본 상대 경로가 바뀌거나 직렬화한 스냅샷이 32 MiB 한도에 가까워지면 이 경계를 다시 검토한다.

Happy CLI PR의 macOS·Linux 스모크 검사에서 상주 번들 시작과 번들 옆 seccomp 필터를 확인한다. 릴리스 승인 뒤 [Happy CLI 릴리스 절차](happy-cli-release.md)로 발행하고, Desktop 런타임 핀과 Windows 패키지를 갱신한다. Desktop 코드 PR은 머지 전에 해당 저장소의 macOS CI를 통과시킨다.
