# Same-conversation personal Claude fallback (source candidate)

This extends the existing dedicated-machine organization rotation. It is Core authentication/session state, not a global `cswap switch`. The Desktop caller must allow personal Claude on this computer and show the account, personal usage charge and automatic organization return before requesting consent.

The new `personal-claude-fallback` encrypted session RPC exposes `status` and `accept`. Status returns a short-lived offer nonce and one positively identified, unowned OAuth account from the local cswap export. Ambiguous/expired accounts, incomplete or changing group custody journals and managed slots are refused. The legacy organization OAuth provenance is also excluded, including known identities whose observation fence is old. An applying/unreadable provenance or a journal/provenance change during export offers no account. Secrets never leave the wrapper process and no personal credential or consent is persisted. The machine login and all other sessions are unchanged. Exiting remote mode restores the prior organization environment instead of carrying a personal token into another mode.

Acceptance requires a Studio-signed, 60-second consent proof for the assigned user, organization, machine, Happy session, original binding nonce, selected account reference and offer nonce. The proof is verified online before applying the local token. Consuming an offer is serialized and one-shot. Cancellation, changed authority, an expired offer or a different account refuses the transition. Possession of a shared conversation key alone cannot mint the owner's consent.

A rejected organization request can continue on the same Claude conversation after consent. While personal is active, organization rate-limit observation/rotation is suspended. At the next user request boundary the wrapper asks the authenticated daemon for current organization authority/quota. `/return` mints only a freshly observed available account, including the original account if it recovered. It persists the normal organization binding before returning credentials. Network/authority/return failures do not silently authorize a new personal request. Expected reset times alone are never success evidence.

Runtime-account v2 advertises support only in a compatible dedicated wrapper, with a process-local transition generation. Personal identity is published after the provider starts with the applied token, and organization identity after return. Older consumers can leave v2 unconfirmed. Older workers keep v1 and expose no usable fallback UI. An organization-only restoration RPC is allowed even after personal use is switched off: it never grants personal execution and waits for an old personal SDK process to stop before acknowledging control delivery. A restart/resume loses temporary personal consent and revalidates the ordinary organization binding first. Conversations originally started with personal login are unaffected.

Validation is offline: injected credentials/authority in unit and real launcher-loop tests, no provider inference. Release/publish, Desktop runtime pin changes and production installation are separate operations and are not performed by this source change.

Organization lookup/authentication errors may offer explicit personal consent only after current member/machine/session authority is verified. Lookup errors exclude explicit access refusals and missing assignments; each personal request rechecks authority online. Changing offer reasons invalidate acceptance. Studio first-seen authentication refusal time, rather than the PC clock, follows both availability and return: the failed generation needs a later successful observation, while a new generation is evaluated normally. Retry only reads status. Quota/authentication-refused turns can continue once after consent, with queued user input taking precedence.

Release candidate: `1.1.10-aplus.358`, based on main `.357`. Merge the Studio authority/consent API first, then merge this CLI source PR. Publishing must use the approved `happy-cli-v1.1.10-aplus.358` GitHub Actions tag flow after explicit release approval. Desktop must keep its existing released pin until that exact registry artifact passes install smoke; do not point it at this unmerged/unpublished source. No wire usage DTO or DB migration is added.

Later requests in a personal provider generation and requests held over a model/provider restart are checked before delivery. A refusal is recorded before ending the SDK input, so even a swallowed later-input rejection produces one failure notice and closes the turn. A refused channel request is bound to its original request ID in the ordered stream and receives a failed reply; it never runs with personal credentials. If a held request restores organization credentials before the SDK starts, options are rebuilt for that credential generation before the request is delivered. Real-launcher and ordering regressions cover ordinary refusal, channel refusal, held-request refusal and held-request organization recovery.

Open design decision before releasing this candidate: personal generations currently use `settingSources: []` to prevent filesystem `env`/`apiKeyHelper` from overriding the selected credential. SDK options supplied by Saycode, mandatory deny rules and application MCP/permission control remain active, but filesystem project/user CLAUDE.md, hooks and permission rules are not loaded. Simply enabling those sources can change the paying account again. Desktop PR #2398 contains a proposed alternative and acceptance checks that preserve those rules while pinning only credential settings; that change awaits direction and is not implemented here. Keep the current released Desktop pin until the design and official artifact release are accepted.
