# daemon 이벤트 루프 멈춤: 세션 저장소 전체 재작성과 거대 transcript

## 배경 (2026-11-10)

공용 PC의 조직 Claude 대화가 "조직 AI 계정의 사용 권한이나 실행 상태를 확인하지 못해 실행을 멈췄습니다"로
계속 실패했다. 직접 원인은 세션 프로세스의 정원 확인 요청(`/setup-token/capacity`, 제한 15초)이 daemon에서
시간 초과된 것이다. 그 실패가 프로세스에 남아 이후 턴을 막은 부분은 buzzni/happy#1216이 고친다. 이 문서는
daemon이 15초 넘게 응답하지 못한 이유를 다룬다.

## 측정

- daemon에 가벼운 요청을 1초마다 10분간 보냈다: 280회 중 3초 초과 25회, 10초 초과 4회, 최대 19.9초.
- 지연이 튄 시각은 daemon 로그의 `Persisted resume cursor` 시각과 겹친다.
- `~/.happy/sessions.json`은 47.7MB, 세션 11,499개(최고 102일 전)다. 보존 기간은 #184에서 의도적으로
  없앴다(오래된 대화 복구). 그래서 저장소는 계속 커진다.
- `persistSession` 한 번은 이 파일을 동기로 읽고 두 번 파싱한 뒤 들여쓰기 JSON으로 다시 쓴다.
  같은 파일 복사본에서 단독 실행해도 2.2~3.1초 걸렸다. daemon(1.2GB, 부하 평균 31/12코어)에서는
  한 번에 3.5~4초였다.
- 커서 저장만 81분에 600회(약 8초에 한 번)였다. 세션마다 30초 간격으로 묶지만 활성 세션이 많다.
- 같은 PC에서 세션 프로세스 4개가 4~5일 동안 590MB transcript를 재개하려다 `ERR_STRING_TOO_LONG`으로
  실패하고 곧바로 다시 실행하기를 반복했다. 각각 CPU 약 90%를 썼다. `claudeCheckSession`이 transcript
  전체를 문자열 하나로 읽기 때문이다. daemon도 같은 함수를 부른다.

## 변경

1. `persistSession`은 이미 파싱한 envelope을 재사용한다(파싱 1회 제거, 구조 변경).
2. `persistSession`은 들여쓰기 없이 쓴다. 47.7MB → 35.7MB. 측정상 쓰기 1회가 2.3~3.1초에서 1~1.7초로 준다.
3. `claudeCheckSession`은 64KB씩 읽어 첫 유효 줄에서 멈춘다. 512MB를 넘는 transcript도 판정한다.

## 비목표와 남은 위험

- 보존 기간을 다시 두지 않는다. 기록이 없는 대화는 같은 세션으로 복구되지 않고 새 세션으로 이어진다
  (`decideUntrackedSessionRecovery`). 기간을 정하는 것은 제품 결정이다.
- 쓰기 1회 비용은 여전히 전체 세션 수에 비례한다. 근본적으로는 커서 저장을 묶어 한 번에 쓰거나
  세션별 파일로 나누어야 한다. 저장소의 내구성 규칙(`publishSessionStoreDurably`, 머신 바인딩 보존)을
  함께 바꿔야 해서 이번 범위에서 뺐다.
- 시작에 계속 실패하는 세션을 쉬지 않고 다시 실행하는 루프(백오프 없음)는 그대로다.
